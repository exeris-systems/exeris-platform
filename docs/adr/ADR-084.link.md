# ADR-084 — WebSocket Provider SPI (link stub)

**Authoritative copy:** [`exeris-kernel/docs/adr/ADR-084-websocket-provider-spi.md`](https://github.com/exeris-systems/exeris-kernel/blob/main/docs/adr/ADR-084-websocket-provider-spi.md)

ADR-084 is a **cross-repo** decision owned by `exeris-kernel`. It binds this repository more tightly than an ordinary awareness stub, for two reasons that are worth stating up front: `exeris-platform` is the **named consumer** whose need reversed a prior ruling, and the surface it gets ships **`preview`**.

## Why this stub exists

RFC-2026-06-18 examined server-push transport and chose SSE, recording WebSocket as "a later, separately-justified addition" for "a use case that doesn't need it yet". That ruling stands as ADR-043 and is still correct for streaming.

Platform LSP is the justification that reverses the WebSocket half of it, and it differs **structurally** rather than by preference: the Language Server Protocol is bidirectional request/response, SSE is one-directional by construction, so LSP cannot ride it. Studio sits on the same connection.

The six requirements ADR-084 is built on are this repository's own:

| Requirement | Why, from here |
|:---|:---|
| Embeddable engine, shaped like `HttpProvider.createServerEngine(HttpConfig)` | The LSP launcher must open a socket without booting a kernel application |
| Text frames | LSP is JSON over the wire; binary is unused |
| Per-connection session identity | One `ExerisLanguageServer` per session — a shared instance would race the workspace index and break `MutationApplyService`'s single-reader-thread assumption |
| A message limit measured against `exeris/applyMutation` | That request carries a serialized `DomainMetadata` baseline; an 8 KB default is orders of magnitude short |
| ADR-043 backpressure — park the virtual thread, never an on-heap queue | Same rule the SSE path already binds |
| Close codes | `exit` without a preceding `shutdown` is a client protocol error, and the socket must be able to say so as the stdio path does with exit code 1 |

## The status that matters: `preview`

ADR-084 ships `preview` at kernel v0.12 **by decision, not by omission**. Its merge gate is a TCK and a binding, and a contract test proves a shape is honoured rather than that it survives; promotion to `stable` is gated on benchmark evidence — concurrent connections, frame throughput, a slow reader, a dead peer — which a TCK structurally cannot supply.

The consequence is recorded rather than left to be discovered: **LSP and Studio are first-party consumers of a `preview` surface for at least one release.** Anyone binding to it here should design for the contract moving, and should not treat a `preview` shape as though `exeris/*`'s own stability rules applied to it.

## When to consult ADR-084 from exeris-platform

- Any work on the Studio ↔ LSP transport. The transport is chosen by ADR-084's shape, not by ours; a third-party WebSocket container is not the fallback (see below).
- Any change to how a session maps to a server instance — the per-connection identity requirement above is what makes one-server-per-session expressible.
- Any change to `exeris/applyMutation`'s payload size profile, which is what the message limit was measured against.
- Before treating the transport as stable: check whether ADR-084 has been promoted out of `preview`.

## Engineering status

**Kernel side:** ADR-084 is **accepted** in the owning repo and its surface shipped **`preview`** in `exeris-kernel` 0.12.0 (`eu.exeris:exeris-kernel-spi` / `-community`, on Maven Central). Promotion to `stable` is still gated on the benchmark evidence described above.

**Platform side: implemented** in `exeris-platform-lsp/src/main/java/eu/exeris/platform/lsp/transport/`, built against `exeris-kernel-spi` / `-community` at the BOM pin. How it meets the requirements above:

- **Embeddable engine:** `LspMain --websocket` opens the kernel's engine directly; no kernel application boots.
- **Text frames:** one WebSocket text message carries one raw JSON-RPC message; `WebSocketJsonRpcFraming` adds and strips the `Content-Length` header LSP4J's stdio codec expects, so the JSON-RPC surface is identical on both transports.
- **Per-connection session identity:** `LspWebSocketConnectionHandler` allocates one `ExerisLanguageServer` per session.
- **Backpressure:** the hand-off from the kernel's `receive()` loop to LSP4J is bounded (`MessageInputStream.CAPACITY`); a full hand-off parks the receiving virtual thread until LSP4J takes a message, and closing the session releases it. There is no unbounded on-heap queue on the inbound path.
- **Close codes:** `exit` after `shutdown` closes with `NORMAL_CLOSURE`; `exit` without `shutdown` closes with `PROTOCOL_ERROR`, mirroring the stdio path's exit code 1.
- **Exposure:** the default bind is loopback only (`127.0.0.1:5007`, path `/lsp`). `exeris/applyMutation` is unauthenticated, so a non-loopback `--host` is refused unless `--allow-remote` is given. The handshake admits only listed browser origins; the default is `http://localhost:4200` and `http://127.0.0.1:4200`, and `--allowed-origin` (repeatable) replaces that default rather than adding to it.

The transport is built on the kernel's own server and nothing else. No third-party WebSocket container, servlet API or embedded HTTP server is a fallback here. If the kernel surface cannot express a need, report it upstream against ADR-084.
