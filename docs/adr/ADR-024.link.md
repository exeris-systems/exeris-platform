# ADR-024 — Capability Composition Model (link stub)

**Authoritative copy:** [`exeris-docs/adr/ADR-024-capability-composition-model.md`](https://github.com/exeris-systems/exeris-docs/blob/main/adr/ADR-024-capability-composition-model.md)

ADR-024 is a **cross-repo, platform-scope** decision owned by `exeris-docs`. It defines the capability contract (`@Provides` / `@Requires` / `@CapabilityModule` / four-phase lifecycle) and build-time DAG validation in `exeris-tooling`, and has been amended three times:

- **2026-06-17 "Validation Stamp Lifecycle"** — stamp *emitted* at tooling, *asserted* at boot, kernel stays cap-blind.
- **2026-06-25 "Composition Runtime Placement"** — the boot conductor and stamp assertion move to an **SDK-side runtime module** (`exeris-sdk-composition-runtime`, schema + content binding in `exeris-sdk-composition-spec`); `exeris-platform` is re-cast as the **deploy-time control plane** (obligation 8c) that *consumes* the composition library — it does **not** host the in-jar boot runtime.
- **2026-07-21 "Boot Conductor Call Site"** — the conductor is **invoked by the generated SKU bootstrap after `KERNEL READY`**, never registered as a kernel `Subsystem`; the kernel bootstrap DAG carries no cap-tier node, and the SKU artefact boots standalone (code detachment).

> Cross-repo link-stub: the authoritative copy lives in the repo named above; the URL resolves to its canonical GitHub location. Convention catalogued in `exeris-docs/adr-index.md` → *Cross-repo stubs*.

## What this means for `exeris-platform`

- **This repo is the control plane, not the composition runtime.** It composes and deploys multi-SKU / mesh / multi-host systems and integrates with external delivery (git, cloud, Kubernetes). It consumes `exeris-sdk-composition-spec` / `-runtime` for design/deploy-time validation and preview. Reintroducing in-jar composition machinery into a Studio/LSP/backend module is a regression against obligation 8c.
- **`exeris-platform-composition-runtime` is a superseded parallel port.** It was the 2026-06-17 realization of the (since-revised) obligation 8; the 2026-06-25 amendment relocates that logic to `exeris-sdk-composition-runtime` and collapses the duplicated content-binding implementation into `exeris-sdk-composition-spec`. Retirement of the platform module (switching the platform BOM to the SDK modules; keeping the golden binding vector as the cross-module conformance pin) is tracked in the gateway-caps implementation plan, Phase 0 (P0.2). Until it lands, do not extend the platform module — new work targets the SDK modules.
- **Do not turn any of this into a security or licensing gate.** The stamp assertion is a *correctness / operability* check (honest-mistake fail-fast), consistent with ADR-023's contractual-enforcement model. A hardened, signature-backed boot gate is a sealed-enterprise-substrate concern with its own ADR.
- **Do not push any of this into the kernel** (obligation 9 — the open kernel stays cap-blind: no stamp check, no manifest reader, no capability/composition type, and — per the 2026-07-21 amendment — no cap-tier `SubsystemProvider` registration either).

## Engineering status

ADR-024 is **ACCEPTED** (amendments through 2026-07-21). The composition runtime's home is `exeris-sdk`; this repo's remaining obligations are consuming the SDK library at the control plane and completing the P0.2 retirement of `exeris-platform-composition-runtime`. The four-phase cap lifecycle conductor (`CapabilityLifecycleHooks` + `initOrder` loop, invoked by the generated SKU bootstrap after `KERNEL READY`) is the still-pending implementation slice — it lands in `exeris-sdk-composition-runtime`, not here. The SKU composition manifest format is fixed as JSON by ADR-053 (2026-07-21).
