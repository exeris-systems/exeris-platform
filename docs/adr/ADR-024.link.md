# ADR-024 — Capability Composition Model (link stub)

**Authoritative copy:** [`exeris-docs/adr/ADR-024-capability-composition-model.md`](https://github.com/exeris-systems/exeris-docs/blob/main/adr/ADR-024-capability-composition-model.md)

ADR-024 is a **cross-repo, platform-scope** decision owned by `exeris-docs`. It defines the capability contract (`@Provides` / `@Requires` / `@CapabilityModule` / four-phase lifecycle), build-time DAG validation in `exeris-tooling`, and — per the **2026-06-17 "Validation Stamp Lifecycle" amendment** — the split of the validation stamp into *emit at tooling* / *assert at platform* / *kernel stays cap-blind*.

> Cross-repo link-stub: the authoritative copy lives in the repo named above; the URL resolves to its canonical GitHub location. Convention catalogued in `exeris-docs/adr-index.md` → *Cross-repo stubs*.

## Why this stub exists

`exeris-platform` **realizes obligation 8** of the amendment: the `exeris-platform-composition-runtime` module is the boot-time composition stamp **assertion** — a generic, once-tested library every SKU bootstrap invokes at startup, before any cap enters `initialize`. It confirms the tooling-emitted stamp in `cap-manifest.json` is present and well-formed, that the content binding matches the deployed cap set, and (multi-manifest) that versions match the classpath — and fails fast otherwise. It does **not** re-validate (no `@Requires`→`@Provides` DAG re-resolution; that stays a build-time concern, obligation 7, in `exeris-tooling`).

## When to consult ADR-024 from the platform

- Touching `exeris-platform-composition-runtime` — the assertion contract (the four checks, the `cap-manifest.json` schema-version handshake, the content-binding algorithm) is fixed by obligations 7–8. The binding algorithm is a **verbatim port** of the tooling's `CompositionStamp#computeBinding`; keep it byte-identical (pinned by a golden test vector) or every deploy false-fails.
- Do **not** turn this into a security or licensing gate. ADR-024's amendment is explicit: because `exeris-platform` is source-available and forkable, this is a *correctness / operability* assertion only. A hardened, signature-backed boot gate is a sealed-enterprise-substrate concern with its own ADR.
- Do **not** push any of this into the kernel (obligation 9 — the open kernel stays cap-blind: no stamp check, no manifest reader, no capability/composition type).

## Engineering status

ADR-024 is **ACCEPTED** (amendment 2026-06-17). Obligation 8 is now **realized in this repo** (greenfield as of the amendment): the validation-stamp assertion ships. Still pending (separate, larger slice): binding the four-phase cap lifecycle (`initialize → ready → drain → terminate`) to the kernel bootstrap state machine — it needs the kernel bootstrap contract and lands later.
