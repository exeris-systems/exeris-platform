# ADR-037 — Isolate the source-model parser/writer in `exeris-sdk-source-model-io` (link stub)

**Authoritative copy:** [`exeris-sdk/docs/adr/ADR-037-source-model-io-module.md`](../../../exeris-sdk/docs/adr/ADR-037-source-model-io-module.md)

ADR-037 is a **cross-repo** decision owned by `exeris-sdk`. It places the 0.3.0 `.java` ↔ `DomainMetadata` parser/writer (JavaParser-based) in a new sibling module `exeris-sdk-source-model-io`, keeping `exeris-sdk-source-model` dependency-light so pure AST-record consumers preserve zero runtime coupling. Driven by [RFC-2026-06-03](../../../exeris-sdk/docs/rfc/RFC-2026-06-03-source-model-parser-writer.md).

## Why this stub exists

`exeris-platform-lsp` is the **primary consumer** waiting on this decision. Its `package-info.java` and the repo README both state the real implementation lands "once `exeris-sdk-source-model` ships its JavaParser-based parser/writer," and the LSP today depends on `exeris-sdk-source-model` for the `DomainMetadata` model. ADR-037 makes that parser/writer a separate coordinate — `exeris-sdk-source-model-io` — rather than folding JavaParser into `source-model`. The LSP must depend on **`exeris-sdk-source-model-io`** (not just `source-model`) to back its custom methods `exeris/entityModel` (read source → `DomainMetadata`) and `exeris/applyMutation` (write `DomainMetadata` → source idempotently).

## When to consult ADR-037 from the platform

- Wiring the LSP's real `exeris/entityModel` / `exeris/applyMutation` implementations — add the `exeris-sdk-source-model-io` dependency to `exeris-platform-lsp/pom.xml`; that is the module holding the parser and the idempotent writer.
- The AST records themselves (`DomainMetadata`, …) still come from `exeris-sdk-source-model`; `-io` re-exposes them transitively, so no duplicate metamodel appears in this repo (consistent with the "one canonical model" rule).
- The 0.5.0 mutation vocabulary (`MutationOp`/`MutationResult`) that `exeris/applyMutation` will speak lives in `exeris-sdk-source-model` (pure records); only the *application* of a mutation to source needs `-io`. Don't redefine the mutation shape platform-side.

## Engineering status

ADR-037 is **ACCEPTED** (2026-06-03). No platform code ships with it — `exeris-sdk-source-model-io` does not exist yet (0.3.0 scaffold pending in `exeris-sdk`). This stub is awareness-only: it records the coordinate the LSP will depend on so the real `entityModel`/`applyMutation` wiring targets `-io` from the start, not `source-model` plus an ad-hoc JavaParser dependency.
