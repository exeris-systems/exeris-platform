# ADR-059 — Data-scope expression: `DataScope { GLOBAL, TENANT, UNIVERSE }` supersedes `tenantScoped` (link stub)

**Authoritative copy:** [`exeris-sdk/docs/adr/ADR-059-data-scope-expression.md`](https://github.com/exeris-systems/exeris-sdk/blob/main/docs/adr/ADR-059-data-scope-expression.md)

ADR-059 is a **cross-repo** decision owned by `exeris-sdk`, shipped in SDK **0.10.0**. `@ExerisDomain.dataScope` — a mutually-exclusive `DataScope { GLOBAL, TENANT, UNIVERSE }` discriminator — becomes the canonical expression of an entity's data-scope tier, and `@ExerisDomain.tenantScoped` is `@Deprecated(since = "0.10.0", forRemoval = true)` with the fallback `true → TENANT` / `false → GLOBAL`. Driven by [RFC-2026-06-24](https://github.com/exeris-systems/exeris-sdk/blob/main/docs/rfc/RFC-2026-06-24-universe-data-scope-expression.md).

> Cross-repo link-stub: the authoritative copy lives in the repo named above; the URLs resolve to their canonical GitHub locations. Convention catalogued in `exeris-docs/adr-index.md` → *Cross-repo stubs*.

## Why this stub exists

`exeris-platform-lsp` is a **read-only consumer** of `DomainMetadata`, which is the record ADR-059 grows. `WorkspaceIndex` holds the canonical metadata and `ProtocolProjections` projects it onto the read-only `exeris/*` wire shapes; the platform neither declares the tier nor decides what it emits. This stub records two things a contributor here should not have to open the SDK ADR to learn.

**The tier has one canonical read, and it is not the field.** `DomainMetadata.dataScope()` is the raw component and is **absent** for every source written before 0.10.0 and for every source that still declares only `tenantScoped`. The canonical read is `DomainMetadata.effectiveDataScope()`, which returns the explicit tier if set and otherwise `tenantScoped ? TENANT : GLOBAL`, and never returns `null`. Whenever the tier is surfaced — a Studio dropdown, a `DomainDescription` field, an `exeris/*` projection — it must come from `effectiveDataScope()`. Reading `dataScope()` directly shows "no tier" for a correctly tenant-scoped entity; reading `tenantScoped()` directly shows the wrong tier once an author declares `UNIVERSE`. Neither fails loudly.

**The tier is a single mutually-exclusive choice, by design.** The whole point of the enum over the boolean is that "shared *and* row-private" is unrepresentable rather than validated away afterwards. If Studio surfaces this, it is one dropdown — not a checkbox that a second control can contradict.

## When to consult ADR-059 from the platform

- Projecting the tier through `ProtocolProjections` — it is not projected today; when it is, use `effectiveDataScope()` and treat the value as always present.
- Anything reading `DomainMetadata.tenantScoped()` — the boolean is deprecated for removal at SDK 1.0.0. A platform-side read of it is a bug that survives compilation until the removal.
- Bumping `exeris.sdk.version` in `exeris-platform-bom/pom.xml` (currently `0.8.0-SNAPSHOT`) past `0.10.0` — see the baseline note below.
- Offering `UNIVERSE` in a design-time surface — it ships **reserved**. The kernel enforces the tier (ADR-012 §4b, kernel 0.11 line), but the `exeris-tooling` transcription that maps it onto the kernel carrier is not built, so declaring it currently has no generated effect. Surfacing it as an ordinary choice would misrepresent what the platform delivers; the SDK's own javadoc carries the honesty note.

## Baseline effect on `exeris/applyMutation`

ADR-059 moves `SchemaVersion.CURRENT` from `"0.9.0"` to `"0.10.0"`. Per [ADR-042](ADR-042.link.md) the mutation applier refuses a baseline written by a different schema version (`SCHEMA_VERSION_SKEW` → `NO_BASELINE`) rather than compare across shapes. So the first workspace built against SDK 0.10.0 will see `exeris/applyMutation` degrade to `NO_BASELINE` until `exeris-tooling` codegen re-runs and re-stamps `exeris-metadata/<entity>.json`. That is the designed behaviour, not a regression — the same one-time skew ADR-054 produced at `"0.9.0"`.

## Engineering status

ADR-059 is **ACCEPTED** (2026-07-31); the SDK side merged 2026-08-02 (`exeris-sdk` **#89**). **No platform code ships with it** — the tier is not projected through any `exeris/*` method and no Studio surface exposes it yet. This stub is awareness-only: it records `effectiveDataScope()` as the canonical read so the first surface that shows the tier targets it from the start rather than the deprecated boolean, and it flags the one-time baseline skew that arrives with the SDK pin bump.
