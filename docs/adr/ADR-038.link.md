# ADR-038 — SDK realization of the capability annotation surface (link stub)

**Authoritative copy:** [`exeris-sdk/docs/adr/ADR-038-capability-annotation-surface.md`](https://github.com/exeris-systems/exeris-sdk/blob/main/docs/adr/ADR-038-capability-annotation-surface.md)

ADR-038 is a **cross-repo** decision owned by `exeris-sdk`. It is the SDK-side realization of [ADR-024](https://github.com/exeris-systems/exeris-docs/blob/main/adr/ADR-024-capability-composition-model.md)'s capability-composition model: `@CapabilityModule` / `@Provides` / `@Requires` / `@CapabilityLifecycle` are defined in `exeris-sdk-annotations`, and the `CapabilityModuleMetadata` / `ProvidesMetadata` / `RequiresMetadata` AST records live in `exeris-sdk-source-model`.

## Why this stub exists

`exeris-platform-lsp` is a **read-only consumer** of the capability AST records this annotation surface produces. The planned `exeris/listCapabilities` LSP method walks the `Capability*Metadata` records (sourced transitively via `exeris-sdk-source-model` / `-io`, exactly as the entity-side `exeris/domains` method consumes `DomainMetadata`) to surface a composition's `@Provides` / `@Requires` graph to Studio and the agent bridge. The platform neither defines the annotations nor performs `@Requires`→`@Provides` resolution — it only reads what the SDK models and the tooling normalizes. This stub records that consumer relationship next to the LSP code so a contributor wiring `exeris/listCapabilities` targets the SDK record shapes rather than inventing a platform-side capability model.

## When to consult ADR-038 from the platform

- Wiring the LSP's `exeris/listCapabilities` method — read the `CapabilityModuleMetadata` / `ProvidesMetadata` / `RequiresMetadata` records via `exeris-sdk-source-model` (re-exposed transitively by `-io`, exactly as `DomainMetadata` is for the entity surface). Don't define a parallel platform-side capability metamodel.
- Consult **ADR-038** for the *record shapes and annotation surface* (what the LSP reads); consult [ADR-024](https://github.com/exeris-systems/exeris-docs/blob/main/adr/ADR-024-capability-composition-model.md) for the *composition semantics and build-time `@Requires`→`@Provides` resolution* — that stays in `exeris-tooling`. The platform reads the graph, it never resolves it.
- The licensing taxonomy (ADR-023) and the `cap-manifest.json` discovery format are deliberately **out** of the SDK record surface — don't expect to read them through these records.

## Engineering status

ADR-038 is **ACCEPTED** (2026-06-05). No platform code ships with it — the `exeris/listCapabilities` method is reserved/planned and the capability annotation surface lands in `exeris-sdk` first. This stub is awareness-only: it records the SDK record shapes the LSP will read so the method targets `Capability*Metadata` from the start rather than a platform-invented model.
