# ADR-042 — Bidirectional mutation surface (link stub)

**Authoritative copy:** [`exeris-sdk/docs/adr/ADR-042-bidirectional-mutation-surface.md`](https://github.com/exeris-systems/exeris-sdk/blob/main/docs/adr/ADR-042-bidirectional-mutation-surface.md)

ADR-042 is a **cross-repo** decision owned by `exeris-sdk`. It locks the mutation surface that LSP / Studio / IDE plugins call: the `MutationOp` vocabulary, the `MutationResult` verdict, AST-level three-way conflict detection (ancestor-or-descendant overlap; convergent edits are `SUCCESS`), baseline-trust gating, and conflict-aware **idempotent** application with an optimistic-concurrency token. Driven by [RFC-2026-06-11](https://github.com/exeris-systems/exeris-sdk/blob/main/docs/rfc/RFC-2026-06-11-source-model-conflict-resolution.md).

> Cross-repo link-stub: the authoritative copy lives in the repo named above; the URLs resolve to their canonical GitHub locations. Convention catalogued in `exeris-docs/adr-index.md` → *Cross-repo stubs*.

## Why this stub exists

`exeris-platform-lsp` **realizes** this decision: `exeris/applyMutation` is the only writer to on-disk `@ExerisDomain` sources, and it delegates entirely to the `exeris-sdk-source-model-io` `SourceModelMutationApplier`. The platform owns neither the mutation vocabulary nor the conflict semantics — both are SDK-owned and cross the wire as JSON conforming to the SDK's Jackson contract (polymorphic on the `op` / `outcome` discriminators). Because LSP4J serializes with Gson (which ignores `@JsonTypeInfo`), the server (de)serializes those payloads with the SDK's Jackson 3 mapper and carries only an opaque `JsonElement` across the LSP4J boundary (see `MutationApplyService`).

## When to consult ADR-042 from the platform

- Touching `exeris/applyMutation` — its wire shape (`MutationOp` in, `MutationResult` out) is frozen by this ADR; do not redefine it platform-side, and do not let a parallel mutation vocabulary appear in `exeris-platform-lsp`.
- Changing the write-back path — the idempotent-write-back contract (the same `MutationOp` applied twice converges to identical on-disk state) is the platform-side obligation this ADR underpins; the platform writes back only on a `SUCCESS` verdict that changes bytes.
- Changing how `exeris/applyMutation` obtains a baseline, which the canonical ADR's **2026-10-07 amendment** ("A Live-Source Caller's Baseline Is the Source Its Token Names") pins. A request may carry `baselineJson` (the last-codegen baseline). A request without one that carries a `concurrencyToken` is judged against the source whose digest is that token: while the live source still has that digest, the server derives the baseline from it under the file lock, stamped with `BaselineTrust.current`; once the source has moved, the SDK applier rejects the op as `STALE_DIGEST`. A request with neither is `NO_BASELINE`. The server never reads build output (`exeris-metadata/*.json`) as a baseline: it may belong to another domain of the same simple name, and it predates the server's own writes. `ApplyMutationTest` pins all three cases.
- A batch / multi-op apply — ADR-042 defers conflict-aware **batch** application; the SDK offers single-op apply only, so the platform applies ops one at a time against the evolving source.

## Engineering status

ADR-042 is **ACCEPTED** and now **realized in this repo**: `exeris/applyMutation` ships, wired to the SDK `SourceModelMutationApplier` (single-op, baseline-trust-gated, optimistic-concurrency token honoured). A change to the `exeris/applyMutation` method surface, to the `MutationOp` / `MutationResult` wire shape, or to the idempotent-write-back contract is visible to ADR-025 (exeris-ai-bridge consumes the `exeris/*` surface) and should re-consult this ADR.
